# Money formatting

`src/lib/utils/money.ts` + `ui/Money.svelte` — how amounts, currencies and the
absent-figure case are rendered. Extracted from `frontend/CLAUDE.md`.


**Never hand-roll `Intl.NumberFormat` for currency.** `formatMoney(amount, opts?, placeholder?)` is the single locale-aware formatter (currency-code driven via `Intl.NumberFormat`, browser locale), and `<Money amount currency? whole? accounting? mono? />` is the component over it. Each amount renders with its **own** ISO 4217 code — never a hardcoded `$`.

- Per-row amounts pass their own `currency` (invoices, credit memos, POs, cards, payments).
- Tenant-wide roll-ups are labelled with the **reporting currency their own payload names** wherever it names one: the dashboard's `reporting.reporting_currency` (every KPI and chart figure on `/`), the cash position's `opening_balance_currency` (the `/cfo` forecast, what-if and position figures, which one `resolve_reporting_currency` call denominates), CFO metrics' `unrealized_fx.reporting_currency` / `reporting_accounts_payable_balance.reporting_currency`, `/payments/summary`'s `currency`, `/discounts`' `currency`. The server resolved that code to denominate the figures, so there is nothing to disagree with (`docs/decisions.md` §160, §200).
- Only a figure with **nothing better to read** — the `/adaptive` thresholds and vendor averages, `/purchase-orders` and the CFO accruals card (until POs record a currency), the zero an empty selection costs — falls back to the `orgCurrency` store (`src/lib/stores/orgSettings.svelte.ts`). It lazy-loads `GET /api/organization` once per session and resolves the code through `utils/reportingCurrency.ts::resolveOrgCurrency`, which reads the response's own top-level `resolved_reporting_currency` FIRST — the exact answer `currency_conversion.resolve_reporting_currency` computed server-side, all four rungs included — and falls back to the pure `resolveReportingCurrency` three-rung client resolution (`settings.reporting_currency` → `settings.payments.home_currency` → `settings.invoice_defaults.currency`) only for a cached or pre-upgrade response that omits the field. **That fallback order still has to mirror the backend's own order exactly**: it is the function deciding what currency the API's cross-currency rollups are actually denominated in, so reading only `invoice_defaults.currency` (as this store once did) mislabelled every aggregate figure for any org whose reporting currency differed — a GBP total rendered with a `$`. `GET /api/organization` is open to every authenticated role, and `resolved_reporting_currency` reaches every role identically — it sits outside the `settings` block, which alone is **projected by role** (`backend/app/services/org_settings_view.py`): a non-admin gets an allow-list that keeps `company` / `invoice_defaults` / `reporting_currency` / `payments.home_currency` / `brand` / `erp.integration_method` (the ingredients the fallback needs) and drops the tenant's third-party credentials, which every role could read before — `payments` is admitted for `home_currency` ONLY, never the processor credentials beside it. If a page needs another settings field client-side, it has to be added to that allow-list on purpose — don't assume the raw blob. Call `orgCurrency.ensureLoaded()` from the page's init `$effect` and read `orgCurrency.currency`.
  - **`orgCurrency.currency` is `string | null`, and `null` is an answer** — before the load lands, and for an org where the server field AND every fallback rung miss (only possible now against a pre-upgrade backend with no operator default configured). The backend's fourth rung, `settings.reporting_currency_default`, used to be operator config no client could read at all, so the store used to substitute `USD` there: a guess indistinguishable on screen from a configured answer, and a `$` on every figure it labelled before it had loaded at all (`docs/decisions.md` §119, §160, §200, followups (c)). Pass it straight to `formatMoney` / `<Money>`, which render a `null` code bare. Mobile's `OrgCurrencyStore` has the same contract.
  - **A form takes `orgCurrency.currency ?? DEFAULT_CURRENCY` itself** — a picker's options (`currencyOptions`), a new record's initial value (`CreateInvoiceModal`, `RequisitionModal`, `IntakeModal`, `ImportStatementModal`, the `/credit-memos` form, the `/expenses` report and pre-approval creates). A select needs *a* value; the store is not where it comes from.
  - **A label that names the denomination takes `orgCurrency.label`** — `Auto-approve below ({currency})`, `Min amount ({currency})`, `CFO sign-off threshold ({currency})`, the `/adaptive` exclusion sentence. It is the code when one resolved, else the localized noun `common.reportingCurrencyUnresolved` ("reporting currency"), which is what the backend compares against whatever it resolves to. `m()` params are `string | number`, so passing `orgCurrency.currency` there is a type error by design. Never pass `.label` to `formatMoney` — a noun is not a code. `i18n/approvalThresholdCurrency.test.ts` pins the call sites.
  - The store is session-cached, so a page that saves one of the three rungs re-resolves it (`orgCurrency.reset(); orgCurrency.ensureLoaded()` — `/organization`'s Invoice Defaults save), or every label on the page keeps naming the answer from before the save.
- **Per-currency subtotals go through `utils/currencyGroups.ts`** — `groupAmountsByCurrency(rows)` buckets a selection by code and sums each exactly (never across codes); `formatCurrencyTotals(totals)` renders one figure per currency, side by side. **A row or total with no usable code is its own group (`currency: null`) and renders bare** — never filed under the org's code, which is what the removed `fallbackCurrency` parameter did: it added money of unknown denomination into the org-currency subtotal, and relabelled a total the backend had reported under `""` (`api/bank_reconciliation.py::_currency_totals`, precisely so it is "not folded into another currency's figure") (`docs/decisions.md` §200). The unknown group sorts last and counts toward `spansMultipleCurrencies`. What an EMPTY input reads as stays the caller's decision — `/payments`' pay bar, `/bank-reconciliation`'s buckets and the `/budgets` / `/expenses` / `/requisitions` KPI cards show a zero in the org's code (bare while it is unresolved), and those three cards show no figure at all (`null` → `KpiCard`'s dash) while their summary has not landed, because an unanswered summary is not an empty one.
- `formatMoney` accepts `number | string-Decimal | null` and returns the placeholder (`—` by default) for null/empty/non-finite.
- **A figure whose currency nobody established renders bare** — grouped figures, two decimals, no symbol — when `currency` is `null`, empty or malformed (`docs/decisions.md` §160, §196). It used to substitute `DEFAULT_CURRENCY`, so every such figure read as dollars on the web while mobile rendered the same row bare. That is the answer, not a degraded mode: a `null` code is where the server refused to guess, and a missing symbol is a gap a reader can ask about where a wrong one is a wrong number that looks right. It is also not the `—` placeholder, which means *no figure*. Two consequences for call sites:
  - **Never write `row.currency ?? orgCurrency.currency`** for a per-row figure. Pass the row's own code — `null` and all. The org's reporting currency is the right label only for a figure the server says is denominated in it, and then the payload usually names it (`reporting_currency`); read that rather than the store.
  - `DEFAULT_CURRENCY` is for **forms** — a picker default, a new record's initial value — never for rendering. `utils/discountRecommendation.ts::formatAmountWithoutCurrency` is now just `formatMoney` with no currency, kept as a name for call sites that withhold one on purpose.
- **A roll-up the server could not denominate is GROUPED, not labelled.** When a total spans currencies and nothing can bridge them (a purchase order carries no locked exchange rate, so no reporting-currency figure exists for it), the server sends one entry per currency and the page renders `ui/MoneyByCurrency.svelte` — one line each, every figure in its own code, the `currency: null` entry bare and never merged into a real one. `/cfo`'s accruals card and by-entity's Open POs column are the two such surfaces (`docs/decisions.md` §197); both used to render one sum under the org's symbol, which is a figure denominated in nothing. Do not "fix" such a total by labelling it — the label is the bug, not the missing symbol.
- **Never type an API money field `number`** — use `MoneyString` (`= string`) or `MoneyAmount` (`MoneyString | number | null | undefined`), both exported from `utils/money.ts`. A `number`-typed money field silently invites `.toFixed()`, `a - b` and `Math.max()` on currency — which is how `/api/analytics/cfo`'s whole response shape ended up violating the Decimal invariant, and how the dashboard came to run `Math.max()` and two bar-width divisions over raw money.

  **Which of the two depends on the endpoint, and the wire is not uniform.** Most surfaces serialise money as an exact decimal string (`/api/payments/summary`, the report builder, the copilot) — type those `MoneyString`. But `backend/app/schemas/money.py::MoneyAmount` deliberately serialises `Decimal` → a JSON **number** at write time (see that module for the >2^53-cents rationale), so `/api/dashboard`, `/api/discounts` and the other schemas using it genuinely send numbers. Typing those `MoneyString` would be a different lie. Type them `MoneyAmount`: it is honest about both shapes, it is what `formatMoney` / `<Money>` accept, and — the point — it makes raw arithmetic a **type error** rather than a convention.

  Where a money value legitimately has to become a `number`, the two purpose-named helpers are the only sanctioned route, and their names refuse the wrong use at the call site: `parseMoneyForLayout` for geometry (a bar width, a `Math.max` that sets a chart's scale) and `isPositiveAmount` / `isNegativeAmount` for a predicate. Never add, subtract or compare two amounts client-side — render both and let the backend own any delta.
- `isPositiveAmount(amount)` / `isNegativeAmount(amount)` are the **predicate** companions — "is this string-Decimal worth rendering at all?" / "should this figure be tinted as a loss?" (zero / null / unparseable → `false` from both). Use them to gate an optional money element (the `/tax` card-excluded column + KPI sub-line) or a loss tint (the CFO unrealized-FX column). They are deliberately NOT money arithmetic: never add, subtract or compare two amounts client-side — render both figures and let the backend own any delta.
- `parseMoneyForLayout(amount)` is the **one sanctioned** money-string → `number` conversion, and it is named for its purpose so the name refuses the wrong use at the call site: chart bar widths, the `Math.max()` that sets a chart's scale, a sort key. The result is a *geometry* input, never a figure — never render it, never fold two of them into a total, never branch a business decision on it. Absent / unparseable → `0`, so a chart can't render a `NaN%` width. All three helpers are covered by `src/lib/utils/money.test.ts`.
- **Money bound for the WIRE is the exact decimal string the user typed** — `utils/moneyInput.ts::normalizeMoneyInput` / `isMoneyInput`, which decide shape with a regex and never touch `Number`. `json.loads` on the server decodes the body before any validator runs, so a fractional JSON number is already a float by the time pydantic sees it and no `Decimal` annotation can undo the rounding. Request-side money fields are therefore typed `MoneyString`, the input holds the RAW text, and text we could not read is **refused** (a toast on `common.amountInvalid`) rather than repaired or quietly sent as `null` — silently dropping an amount the user typed is the same class of failure as rounding it. Converted so far: `/budgets`, `/intake`, `/recurring`, and the Positive Pay presented-items paste (whose amount decides whether a cheque was ALTERED, so an unreadable figure must never degrade to "no amount", which the classifier reads as a clean match).
- **The conversion is ratcheted, not swept** — `src/lib/types/moneyTypeAudit.ts` + `.test.ts`. A scan of `src/lib/types/*.ts` for money-shaped `number` fields returns ~105 candidates and **most are not money** (`total` is a pagination row count on every list envelope, `budget`/`remaining` are *token* counts on the assistant meter, `limit` is a report row cap), so a blanket retype cannot land first. The test carries a per-module `BASELINE` that may only ever decrease, a `CONVERTED` list pinned at zero, and a `JUDGED_NOT_MONEY` map recording each per-field judgment **with its reason** — the only honest way to tell a count from an allocation. Converted modules: `accessReview`, `assistant`, `budget`, `exceptionAgents`, `intake`, `notification`, `positivePay`, `privacy`, `recurring`, `reports`, `vendor`. Still `number`-typed (baseline in the test): `catalog`, `contract`, `discounts`, `expense`, `invoice`, `payment`, `requisition`, `vendorStatementRecon`, `workflow`.
- The type-level half of that guarantee is a block of `@ts-expect-error` probes at the bottom of `moneyTypeAudit.test.ts`: one per converted module, each a real arithmetic expression on a real money field. TypeScript fails an *unused* `@ts-expect-error`, so retyping any of those fields back to `number` turns **`pnpm check`** red as well as the unit test. Resolve a genuine compile error with `parseMoneyForLayout` / `isPositiveAmount` — **never an `as` cast**, which puts the hazard straight back.
- **i18n-aware locale** — when a caller passes no explicit `locale`, `formatMoney` defaults to the active in-app locale (the i18n picker), read from `$lib/i18n/formatLocale.ts::getActiveFormatLocale()`. Until a locale is actively selected the holder is `undefined` (browser locale), so nothing changed pre-i18n. Selecting German in the picker makes `$1,234.50` render as `1.234,50 $`. **`utils/time.ts`'s `formatDate` / `formatPeriod` date helpers read the same holder**, so dates switch locale alongside money (German renders `Jun 20, 2026` as `20. Juni 2026`). Both parse bare `YYYY-MM-DD` / `YYYY-MM` keys at *local* midnight (not UTC) so a negative-offset timezone can't roll the displayed day back. `formatDate` takes an optional `Intl.DateTimeFormatOptions` third arg so a caller can vary the parts (no-year for a due-date cell, date+time for a queue row — it auto-switches to `toLocaleString` when `hour`/`minute`/`second` is asked for) while still localizing off the active locale; omit it for the standard short date. The per-row date cells on the **dashboard** (due dates), **payments** (created/executed/expiry), the **exceptions** queue, and the **workflows** / **discounts** / **credit-memos** / **vendor-statements** lists (plus the `VendorStatementReconModal` dialog) have been migrated onto this shared helper — they previously hardcoded `en-US` so the picker didn't move them. The **admin** lists (`admin/webhooks`, `admin/api-keys`, and the `UsersPanel`, which each hardcoded `en-US`) and the **supplier-portal** lists (`portal/invoices`, `portal/payments`, `portal/purchase-orders`, `portal/discount-offers`, which each hand-rolled a per-page `fmtDate` on a locale-less `toLocaleDateString()`) are now migrated too — note the portal cells shifted from the browser's numeric short date (`6/20/2026`) to the shared helper's month-name short date (`Jun 20, 2026`, locale-driven), and keep the portal's `m('portal.common.dash')` placeholder by passing it as `formatDate`'s 2nd arg. Remaining inline `toLocaleDateString` call sites elsewhere (procurement lists; the `tax` + `audit` consoles, which already follow the *browser* locale but not yet the picker) are not yet migrated (a later slice).
