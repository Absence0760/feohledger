# Internationalization (i18n)

The Flutter app's localization setup — ARB catalogues, the generated
delegate, locale negotiation, and the locale-aware formatting helpers.
Extracted from `mobile/CLAUDE.md`. The web counterpart is `frontend/docs/i18n.md`.


Multi-language UI via the **idiomatic Flutter `gen-l10n` + `intl` + `.arb`**
path — the mobile counterpart of the web `frontend/src/lib/i18n/` runtime.
Same six locales (en, de, fr, es, pt-BR, ja) and the same ICU plural shapes.

- **Catalogues** — `lib/l10n/app_<locale>.arb`. `app_en.arb` is the
  source-of-truth template (with `@key` placeholder metadata); the others
  translate its values. ICU plurals (`{count, plural, one {…} other {…}}`) and
  `{placeholder}` substitution are used where the web uses them. Japanese has
  no grammatical plural, so its plural blocks carry only an `other` arm.
  `app_pt.arb` is a base-Portuguese fallback that gen-l10n **requires**
  alongside the script/country `app_pt_BR.arb` (same content).
- **Config** — `l10n.yaml` drives generation; `flutter: generate: true` in
  `pubspec.yaml` wires it into the build. Output is **committed**
  (non-synthetic): `flutter gen-l10n` writes `AppLocalizations` into
  `lib/l10n/gen/` (in the tree, reviewable, travels with a clone — recent
  Flutter dropped the `synthetic-package` flag; an explicit `output-dir` is
  what lands it in the tree). **Re-run `flutter gen-l10n` after editing any
  ARB** and commit the regenerated `gen/` files.
- **Reading strings** — `AppLocalizations.of(context).<key>` (e.g.
  `l.navInvoices`, `l.dashboardInvoiceCount(n)`). A widget under test needs
  `localizationsDelegates: AppLocalizations.localizationsDelegates` +
  `supportedLocales: AppLocalizations.supportedLocales` on its `MaterialApp`
  (no explicit `locale` → defaults to `en`, so English assertions hold).
- **Per-device locale** — language is a **device** choice (like the biometric
  toggle), NOT account-roamed. `LocaleStore` (`stores/locale_store.dart`, a
  `ChangeNotifier` singleton) persists the choice locally via
  `flutter_secure_storage` and never sends it to the backend. `main.dart`
  wraps `MaterialApp` in a `ListenableBuilder` on `LocaleStore.instance` and
  passes `locale: LocaleStore.instance.locale` (`null` = follow system) so a
  picker change re-localizes the whole tree live. The picker lives in
  **Settings** (`settings_screen.dart`) — endonyms (English / Deutsch /
  Français / Español / Português (Brasil) / 日本語) plus a "System default"
  entry that clears the override.

- **Currency** — every money figure goes through `lib/utils/money.dart`
  (`mobile/CLAUDE.md` § Money formatting holds the rule). It resolves the
  symbol and the **minor-unit count** from the ISO code via
  `NumberFormat.simpleCurrency`, so JPY renders `¥1,235` with no decimal
  places while USD renders `$1,234.56` — the nine module-level
  `NumberFormat.currency(symbol: '\$')` declarations it replaced got both
  wrong for every non-USD tenant.
- **Format locale** — `lib/utils/format_locale.dart` is the seam between the
  picker and the `intl` formatters, the mobile mirror of the web
  `i18n/formatLocale.ts`. **The ISO code and the reader's locale answer
  different questions**: the code says what a figure IS (symbol, minor units)
  and comes from the payload; the locale says how a reader writes a number or
  orders a date, and comes from the device. A EUR figure is `€1,234.50` to an
  `en` reader and `1.234,50 €` to a `de` one; `Mar 4, 2026` is `4. März 2026`.
  - `activeFormatLocale` is what `money.dart` and `dates.dart` default to;
    `FormatLocaleScope`, mounted in `MaterialApp.builder` (so it sits under
    `Localizations`), keeps it equal to the locale MaterialApp **resolved** —
    which handles "follow the system locale" and an unsupported device locale
    without re-deciding either.
  - A figure already on screen re-formats because the locale change rebuilds
    every element depending on `Localizations` — which is every screen, via
    `AppLocalizations.of(context)` — so words and figures ride one rebuild.
  - `setActiveFormatLocale` deliberately leaves `Intl.defaultLocale` alone: a
    global default with no loaded date symbols turns every locale-less
    `DateFormat` into a throw, including the fallback in `dateFormatLocale`.
    The two formatting modules pass the locale explicitly instead.
- **Dates** — `lib/utils/dates.dart` is the date half of `money.dart`, and the
  only module allowed to construct a `DateFormat` (`test/utils/dates_test.dart`
  fails on a second one, and on a `NumberFormat` outside `money.dart`). Two
  rules it exists to enforce: the pattern is a **skeleton**
  (`DateFormat.yMMMd`), never a literal — `DateFormat('MMM d, yyyy', 'de')`
  renders "März 4, 2026", English word order wearing German words — and the
  formatter is built **per call**, because the ten module-level
  `final _dateFormat = …` declarations it replaced froze the locale at import
  and would have survived a picker change. `formatIsoDate` is the deliberate
  exception: a wire format, never rendered.
- **Invoice warnings** — the findings on the invoice-detail panel are composed
  per row by the backend ("PO 4412 not found", a variance, an amount), so a
  label per `type` could never state one: a single type is up to five
  sentences. The backend therefore emits a stable `code` plus typed `params`
  beside the English `message` (`backend/docs/invoice-warnings.md`), and
  `lib/l10n/invoice_warning_messages.dart` resolves that pair to an ARB key
  (`invoiceWarning<Code>`, all 48 of them in all six locales) and
  locale-formatted parameters. `invoiceWarningText(l, warning)` is the only
  way a warning reaches the screen.
  - **It falls back to `warning.message`, and that is a normal path**, not an
    edge case: an unknown/absent code (every row persisted before the backend
    catalogue existed carries none, and nothing backfills) or a missing
    parameter both yield the server's own complete English sentence, which
    beats a half-filled translated one.
  - **The catalogue is generated, not hand-authored.** The code → sentence
    dispatch and the parameter-kind map are
    `lib/l10n/invoice_warning_messages.generated.dart`, a `part` of
    `invoice_warning_messages.dart`, written by `pnpm gen:warning-messages`
    from `backend/app/services/invoice_warning_catalog.py` in the same run, from
    the same catalogue, as the web's
    `frontend/src/lib/api/invoiceWarningMessages.generated.ts` — so the two
    surfaces cannot hold different codes or kinds. Dart has no string-keyed
    lookup into a gen-l10n class, so where the web generator emits a key per
    code, this one emits a `switch` arm per code calling the right
    `AppLocalizations` method. The **argument order and type are read from
    `app_en.arb`'s placeholder metadata** (what `flutter gen-l10n` builds the
    signature from), because two `String` arguments swapped would compile and
    put a PO number where the amount belongs; an ARB whose placeholders don't
    match the catalogue makes the generator refuse. The guard chain, one step
    each: `pnpm check:warning-messages` (CI's Backend lint job) fails on a
    stale file — including when only the ARB's placeholder order moved; a
    regenerated arm calling a message `app_en.arb` lacks fails
    `flutter analyze`; `test/l10n/arb_parity_test.dart` demands the other
    locales. `test/l10n/invoice_warning_messages_test.dart` then proves every
    generated arm reaches a real sentence in every locale. Round 26
    hand-transcribed all 48 arms and backstopped them with a test parsing the
    TypeScript; generating the Dart half retired both. **Never edit the
    generated file by hand** — change the catalogue (or the ARB) and
    regenerate.
  - A parameter's **kind** decides its formatting: `money` renders through
    `formatMoneyString` in the invoice's own currency (which the params carry),
    `percent` / `number` through `utils/numbers.dart` at the precision the
    backend measured, `date` through `formatDate`, and a plural selector stays
    an `int` so ICU can choose its arm.
- **`adaptivePatternsCurrencyNote`** is now *conditional*: the adaptive
  patterns tab renders it only when no reporting currency could be resolved,
  because with one the figures carry their own symbol and the note has nothing
  left to explain.
- **Tests** — `test/l10n/arb_parity_test.dart` is the ARB key-parity guard
  (mirrors the web `messages_parity`): every locale ARB has exactly the
  template's key set, no empty values, and the same placeholder *set* (deduped
  — a 1-arm `ja` plural compares equal to a 2-arm `en` one).
  `test/l10n/locale_switch_test.dart` proves the `LocaleStore` →
  `MaterialApp.locale` plumbing re-localizes a visible string live **and that
  the figures switch with the words** (a money amount and a date, through the
  same `FormatLocaleScope` wiring `APApp` uses — the picker used to change
  every word and not one digit), and carries
  a per-batch guard asserting each extraction round's new keys switch with the
  locale (the notifications/vendors/exceptions/payments batch, the
  approvals/capture/advanced-search batch, the invoice-detail batch
  (detail/edit/warnings/ERP/file-viewer, incl. the `invoiceDetailErrorPrefix` +
  `warningsVarianceLabel` placeholders), the payment-queue batch (Pay
  tabs/summary/runs, incl. the `paySelectedCount` plural + `payRunExecuteFailed`
  placeholder), the login / admin / org-settings / workflows batch (incl. the
  `workflowsStepCount` plural + `orgSettingsSaveFailed` / `adminUsersActivated` /
  `workflowDetailStepNumber` placeholders), and the inspections / adaptive batch
  (incl. the `adaptiveAnomaliesScanned` plural and the `inspectionsResultAnnounce`
  / `inspectionRecordReceiptsBounded` / `adaptivePatternsLookback`
  placeholders)). When a screen or shared sub-widget is
  localized, every existing
  widget/screen test that pumps it must wrap the subject in a `MaterialApp`
  carrying `AppLocalizations.localizationsDelegates` + `supportedLocales` (a
  `_localized` / `_host` / `_screenHost` helper), or `AppLocalizations.of`
  returns null at runtime. Do NOT call `AppLocalizations.of(context)` from a
  widget's `initState` (the `Localizations` inherited widget isn't available
  yet — `dependOnInheritedWidgetOfExactType … before initState() completed`);
  resolve a flag in `initState` and localize the message in `build`, as
  `invoice_file_viewer` does for its PDF-load error.
